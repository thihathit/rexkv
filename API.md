# rexkv API

rexkv is two layers:

- **Native (Rust + redb)** — the `.node` addon. Bytes in / bytes out; serialization (JSON etc.) is the caller's job.
- **TS library (`ts/`)** — a small source-only npm package (`rexkv`) layered on the native bindings: `JsonTable`, the JSON serializer, and helpers.

```
                ┌──────────────────────┐
  your app  ──▶ │  TS library (ts/)    │   JsonTable, serializeJSON,
                │  rexkv npm package  │   deserializeJSON, getKvStore
                └──────────┬───────────┘
                           │  Buffer keys/values
                ┌──────────▼───────────┐
                │  Native .node addon  │   KvStore, KvTable (NAPI-RS + redb)
                │  (Rust bindings)     │
                └──────────┬───────────┘
                           ▼
                      redb database file
```

---

## Design decisions

rexkv dictates one mode per operation — there is no `put` **and** `putAsync`. The split is by cost, tuned so the JS event loop never tanks:

- **Sync — the hot path.** Operations that are cheap and that tight loops depend on: single-key reads (`get`), structural calls (`openTable`, `name`). `openTable` is sync _and_ does no I/O — it just returns a handle; the table is created lazily by the first write to it, and reads on a never-written table return `null`. Reads don't fsync and don't take redb's write lock, so they're safe on the JS thread.
- **Async — everything that writes or scales.** `put`, `putBatch`, `delete`, `remove`, and bulk reads (`getBatch`). These commit to disk and can block for unbounded time, so they run on worker threads and resolve via Promise. The event loop stays responsive during fsync.
- **Why not symmetric:** a `put` + `putAsync` for every op doubles the surface and lets users accidentally block the loop. Dictating one mode keeps the hot path lean and the slow path safe by construction.
- **Worker layout:** all off-thread work — writes and bulk reads (`getBatch`) — runs on one ordered worker thread (redb is single-writer, and sharing the queue keeps reads serialized with writes for free). The hot single-key read (`get`) runs sync on the JS thread. A bounded queue provides backpressure — when it's full, `put` rejects instead of letting memory grow.
- **Call order is queue order:** each op enqueues _synchronously on the JS thread_ before the promise is handed back, so the queue order is exactly the caller's order — no reordering by worker scheduling. `close()` enqueues the same way, so a write issued after `close()` is deterministically rejected, never applied silently, and never left pending.
- **Durability** is a constructor option (`immediate` / `eventual` / `none`, mapping to redb `Durability`). `eventual` drops fsync per commit and is often 10–100× write throughput; `immediate` is the default for safety.
- **Serialization is JS-side and stays sync.** `serializeJSON`/`deserializeJSON` are stringify/parse on the JS thread; only the resulting bytes cross into the worker.

## Part 1 — Native bindings (Rust, exposed as `.node`)

Exports one class: `KvStore` (declared in `ts/types.d.ts`, generated by NAPI-RS). Bytes in / bytes out.

### `KvStore`

| Member      | Signature                                             | Description                                                                                                                                        |
| ----------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| constructor | `new KvStore(path: string, options?: KvStoreOptions)` | Open (or create) a redb database file. `options` tune `durability`, `maxQueue`, `compression`.                                                                    |
| `openTable` | `openTable(name: string): KvTable`                    | Open a named table. Sync, no I/O: returns a handle; the table is created lazily by its first write. Throws `"database is closed"` after `close()`. |
| `close`     | `close(): Promise<void>`                              | Drain the write queue, flush, and close. Async — never drops queued writes. Every later op throws `"database is closed"`.                          |

### `KvTable`

| Member     | Signature                                               | Mode     | Description                                      |
| ---------- | ------------------------------------------------------- | -------- | ------------------------------------------------ |
| `name`     | `get name(): string`                                    | sync     | Table name.                                      |
| `get`      | `get(key: Buffer): Buffer \| null`                      | **sync** | Fetch value, or `null` if key missing. Hot path. |
| `put`      | `put(key: Buffer, value: Buffer): Promise<void>`        | async    | Insert or overwrite.                             |
| `delete`   | `delete(key: Buffer): Promise<boolean>`                 | async    | Remove key; resolves `true` if it existed.       |
| `remove`   | `remove(key: Buffer): Promise<boolean>`                 | async    | Alias of `delete`.                               |
| `putBatch` | `putBatch(entries: KvEntry[]): Promise<void>`           | async    | Insert many entries in one transaction.          |
| `getBatch` | `getBatch(keys: Buffer[]): Promise<(Buffer \| null)[]>` | async    | Bulk read; one value per key, in order.          |

### `KvStoreOptions`

```ts
interface KvStoreOptions {
  durability?: "immediate" | "eventual" | "none"; // default "immediate"
  maxQueue?: number; // default 1024; backpressure cap
  compression?: "none" | "lz4"; // default "lz4"; must match when reopening a file
}
```

`compression: "lz4"` (the default) LZ4-compresses value bytes on the writer
thread before storing (only when the compressed form is actually smaller) and
decompresses on read. `compression: "none"` writes values byte-for-byte,
identical to the original on-disk format. Compression is a **per-store policy**:
a file must be reopened with the same setting. Pass `compression: "none"` when
reopening a file written before `"lz4"` became the default — with the default,
a legacy `"none"`-format value whose first byte is `0x00` or `0x01` is misread
(a stripped byte or a decompression error), so mismatched modes are
unsupported. For compressible data `"lz4"` typically cuts the database file
~9x and can speed up reads by shrinking the working set; incompressible data is
stored raw (no harm, slightly more CPU).

### `KvEntry`

```ts
interface KvEntry {
  key: Buffer;
  value: Buffer;
}
```

### Semantics (native layer)

- Keys/values are raw bytes. Content equality decides a hit; ordering is byte-lexicographic (redb B-tree).
- Tables are created lazily: a table exists after its first write. Until then, `get`/`getBatch` on it return `null` — `openTable` itself is sync and allocation-free.
- Async ops on one table are ordered: a `put` enqueued after another is applied after it. `get` sees whatever is committed; to read your own writes, `await` the write first.
- The writer thread stays alive in a "closing" mode after `close()` drains, rejecting any job that arrives late — so a write racing `close()` either commits (issued first) or rejects (issued after), deterministically. The thread exits once the store and its tables are garbage-collected.
- Tables share one database file; identical names open the same table.
- The JS thread never runs a write transaction or fsync; all writes and bulk reads are off-thread.

## Part 2 — TS library (`ts/`, npm package `rexkv`)

Source-only package (`files: ["index.ts", "types.d.ts"]`); re-exports the native types so one import covers both layers:

```ts
import { JsonTable, getKvStore } from "rexkv";
const KvStore = getKvStore(require("./rexkv.linux-x64-gnu.node"));
```

| Member            | Signature                                               | Description                                                     |
| ----------------- | ------------------------------------------------------- | --------------------------------------------------------------- |
| `getKvStore`      | `getKvStore(module: unknown): typeof KvStore`           | Unwrap the `KvStore` constructor from a loaded `.node` module.  |
| `serializeJSON`   | `serializeJSON(value: unknown): Buffer`                 | JSON-encode to bytes, restoring non-JSON types on decode.       |
| `deserializeJSON` | `deserializeJSON<T>(bytes: Buffer): T`                  | JSON-decode bytes from `serializeJSON` (or any JSON).           |
| `JsonTable`       | `new JsonTable(table: KvTable)`                         | JSON de/serializer wrapper over a byte table.                   |
| types             | `KvStore`, `KvTable`, `KvEntry`, `JsonKey`, `JsonEntry` | Native types re-exported / library types defined in `index.ts`. |

### `JsonTable<K, V>`

`K extends JsonKey = JsonKey` is the key type (`Buffer`, `string`, or a union), `V = unknown` the value type; `get`/`getOr` return `V` / `V | null`. Mirrors the native mode split — reads are sync, writes are async.

| Member              | Signature                                                  | Mode     | Description                                                                 |
| ------------------- | ---------------------------------------------------------- | -------- | --------------------------------------------------------------------------- |
| `raw`               | `readonly raw: KvTable`                                    | —        | Underlying byte table.                                                      |
| `name`              | `get name(): string`                                       | sync     | Table name (delegates to `raw`).                                            |
| `get`               | `get(key: K): V \| null`                                   | **sync** | `deserializeJSON` the value; `null` if key missing or value is JSON `null`. |
| `getOr`             | `getOr(key: K, fallback: V): V`                            | sync     | Fallback when the key is missing.                                           |
| `put`               | `put(key: K, value: V): Promise<void>`                     | async    | `serializeJSON` and store; string keys are utf8-encoded.                    |
| `putBatch`          | `putBatch(entries: { key: K; value: V }[]): Promise<void>` | async    | Encode and insert in one transaction.                                       |
| `delete` / `remove` | `delete(key: K): Promise<boolean>`                         | async    | Passthrough to the byte table.                                              |

`JsonTable` stores serialized bytes, so a value read back with `get` and put back with `put` (even nested inside a larger structure) keeps its full fidelity without re-serializing its internals — see per-level metadata below.

### Serialization (`serializeJSON` / `deserializeJSON`)

- Restores values JSON can't round-trip. A detection pass (single `JSON.stringify` whose replacer reads `this[key]`, the pre-`toJSON` value) finds them and also rewrites values `stringify` can't handle (e.g. `BigInt`); if none are found the pass output is used as-is, with no metadata and no extra work.
- When special values exist, a second pass copies the tree from the original value. Each level (plain object or array) that directly holds one gets one short `"__$p"` metadata key mapping short relative paths (bare property names, plus array indices) to type tags, e.g. `{ "at": "...", "__$p": { "at": "date" } }`. Nested plain objects/arrays in the data serialize as ordinary JSON — their tags are recorded on their own level.
- Levels with no special children are not copied. When the root itself is not a plain object (array, `Date`, `Map`, …) the value is wrapped as `{ "__$p": …, "__$v": … }`. `deserializeJSON` revives deepest paths first, unwraps `"__$v"`, and deletes `"__$p"` after restoring that level.
- Supported types (metadata tag in parentheses): `Date` (`date`), `Buffer` (`buffer`), `Uint8Array` (`uint8array`), `Map` (`map`), `Set` (`set`), `RegExp` (`regexp`), `BigInt` (`bigint`), `NaN` (`nan`), `Infinity`/`-Infinity` (`infinity`/`-infinity`).
- The `"__$p"` and `"__$v"` keys are reserved — passing data that already contains them throws.
- `undefined` is dropped and `null` stays `null`, per JSON semantics.
- `Symbol` values and custom class prototypes are dropped (not JSON-representable and not generically restorable); other typed arrays (e.g. `Int32Array`) serialize via their `toJSON` shape without special restore.

## Limitations

### No true zero-copy reads

redb does not memory-map its database file: values are read from disk into an in-memory
page cache, and a read hands back bytes borrowed from one of those cached pages. The
borrowed slice lives only as long as redb's `AccessGuard`, which is pinned to the read
transaction — once the guard (or transaction) drops, the cache may evict or reuse the
page. redb provides no way to detach a pointer and keep it valid independently of a
transaction.

Returned values are therefore copied before they reach JS: napi transfers the bytes to
the JS heap as a `Buffer` at promise-resolution time. True zero-copy reads would require
the engine to expose stable pointers whose lifetime can outlive a transaction — the way
mmap-based engines (e.g. LMDB) do — which redb's storage model does not. Even then, Node
builds with the V8 memory cage (e.g. Electron) reject external buffers entirely and fall
back to copying, so zero-copy cannot be relied on in every runtime.
